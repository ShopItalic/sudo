P10 cleanup: risks before hardware

The release gates are recovery, runtime stability and recording custody. A successful build cannot establish any of those on a physical Ring.

P10 test candidate. Write-ahead retry accounting, storage handoffs and iPhone receipt integration are implemented. Software verification and packaging are recorded below. Physical recovery and qualification remain separate; no P10 Ring flash has been performed.

What the earlier incident tells us

The saved S05 audit reproduced interrupt-triggered resets in the GNU C-library lock backend and a motor task using 664 bytes against a 512-byte stack. The first fault on the physical Ring was not captured, so this does not establish that deletion itself caused the brick. The supplied bootloader configuration lacked an independently demonstrated recovery entry if the application kept crashing.

P10 keeps the supplier ArmCC5 toolchain and leaves the bootloader, SoftDevice and board selection outside its change set. This avoids repeating the specific toolchain switch; it does not prove that new scheduling, storage or memory behavior is safe. See the firmware incident audit, F1 and F5 and qualification workflow.

Prioritized risks

Priority reflects consequences and unresolved evidence. Physical failure probabilities are unmeasured; they are not inferred from host test counts. Owners below describe the responsible workstream.

Critical · hardware gate

1. A crash prevents its own repair

A valid application that resets before Bluetooth recovery can leave the Ring unreachable. A firmware rollback button in the app is ineffective if the app cannot connect.

Required: demonstrate restoration of the exact factory image on the identified spare using a verified recovery route. Preserve that image, configuration and recovery procedure. Do not infer recovery from a charging case or generic debug-pad guidance.

Impact: high · Likelihood: unmeasured; historical incident
Owner: firmware / hardware · Status: open
Critical · runtime gate

2. Stack, heap or interrupt failures

Hashing, filesystem calls and logging can exhaust task stacks, delay critical work or call an API from the wrong execution context. Enlarging one task stack also consumes the shared runtime heap.

Required: keep cleanup in task context; check linked call paths and allocation failures; measure stack and heap headroom while recording, transferring, hashing and reconnecting. P10 allocates 4,096 bytes to the BLE worker, 2,048 more than P09. The factory stack-overflow checking option is disabled.

Impact: high · Likelihood: unmeasured on P10
Owner: firmware runtime · Status: static checks and hardware measurements required
Critical · storage gate

3. Cleanup overlaps recording or transfer

Two users of the same filesystem, or one task powering down flash during another task's work, can corrupt state or stop a recording. The draft audit found an early-idle reservation race and a close-before-power-down ordering gap.

Implemented locally: reservations identify their owning task; close keeps ownership until completion; cleanup observes capture ownership through rollover and finalization. Error closes retain a busy state. The linked recording, transfer, enumeration and status paths were audited. Counted task notifications prevent lost wakeups. Worker faults retain BUSY without returning from an RTOS task, reads/seeks/closes are checked, and directory copies are bounded. Recording-start latency still needs measurement on the spare.

Impact: high · Likelihood: defects observed in the first draft
Owner: firmware storage · Status: source audit and host integration checks complete; physical qualification open
Critical · custody gate

4. A stale receipt deletes another recording

A timestamp or filename can be reused. A queued deletion must refer to the exact object copied to the phone, including after reboot, reconnect, account change or switching Rings.

Required: capture a persistent random recording ID before transfer, bind it to exact raw byte count and SHA-256, durably save and verify the phone copy, then persist the Ring receipt before acknowledging it. Recheck identity and content before removal. A queued receipt is not a delete acknowledgement.

Impact: high · Likelihood: unmeasured
Owner: iOS sync / firmware protocol · Status: firmware and iOS receipt integration implemented and tested
Critical · power-loss gate

5. Power fails while metadata changes

Receipt creation and file deletion both write filesystem metadata. LittleFS is designed for power-loss resilience, but the exact driver, flash behavior and surrounding code must preserve its assumptions.

Implemented locally: checked I/O, receipt readback before ACK, no format on mount failure, no low-space reclamation of older unacknowledged files. A RAM NOR fixture exercises 30 interrupted mutations and repeated power cuts before failure bookkeeping. Fragmented storage above 93% occupancy, repeated attribute commits, remounts and neighboring recordings are also tested. Actual flash power interruption remains a physical test.

Impact: high · Likelihood: unmeasured on fitted flash
Owner: firmware storage / hardware · Status: host coverage only
LittleFS design: power loss, wear and bounded memory
High · performance gate

6. Retry work drains power or delays recording

A stuck file can cause repeated scans, full hashes and flash writes. A 512-byte hash slice is not a wall-clock guarantee: metadata operations can take longer, and large recordings need many slices.

Implemented locally: idle-only slices, backoff and a five-attempt cap. Every attempt is committed and read back before hashing or removal begins. A reset can consume an unused attempt, but cannot restore the budget. Only an explicit app Retry resets an exhausted receipt. Measure capture latency, dropped audio, BLE responsiveness, battery use and backlog recovery.

Impact: high · Likelihood: unmeasured
Owner: firmware runtime / iOS sync · Status: interrupted-attempt accounting fixed and tested; physical timing and power open
High · compatibility gate

7. App and firmware disagree about cleanup

The prototype disables legacy filename deletion and formatting. An old app cannot use the new receipt protocol. Existing recordings and partially transferred files need a conservative migration path.

Required: explicit capability negotiation, correct handling of busy/pending/failed/absent states, idempotent retries and cancellation, and tests for old app/new firmware, new app/old firmware, upgrades and downgrades. Carry the latest P09 capture-busy and battery fixes into the exact P10 snapshot.

Impact: high · Likelihood: incompatibility known without matching app
Owner: iOS sync / release · Status: matching app integration complete; physical compatibility qualification open
High · evidence gate

8. Passing tests qualify a different artifact

The first host run printed success despite a sanitizer warning. The first firmware build also predates the subsequent concurrency fixes. Neither result can be used to approve a later image.

Implemented locally: fatal sanitizer findings, negative controls that deliberately reintroduce the race and unsafe SHA byte shift, immutable build directories, and a verifier that compares generated code to the current recipe. Bind every result to source and artifact hashes.

Impact: high · Likelihood: evidence gaps observed during development
Owner: firmware validation / release · Status: safeguards added; physical proof separate

Recommended sequence

  1. Complete the test release checks. Freeze the source, verify the licensed image and independently verify the application-only signed ZIP. Keep the matching iPhone app with this candidate.
  2. Demonstrate spare-device recovery. This precedes any P10 hardware test. Flashing still requires an explicit request and verified target.
  3. Begin physical checks without cleanup authority. Verify boot, reconnect, recording, transfer and descriptor hashing before issuing any receiver receipt. Unconfirmed descriptors cannot authorize removal. Measure memory and recording responsiveness.
  4. Test actual cleanup on the recoverable spare. Use known recordings with verified external copies; interrupt power, transfer and reconnect at controlled boundaries. Verify every surviving recording byte-for-byte.
  5. Release the exact qualified image. Preserve artifacts and their evidence. Do not treat host tests, compilation, signing or installation as physical qualification.
