Bluetooth reconnect stops an active local recording

Defect reproduced in released P10-r2 source. Source fix implemented in new P11-r3 and P11-r4 recipes, plus a P10-r4 fallback, and tested on the host. No new ArmCC5 image, release package, or Ring installation.

Confirmed in source and a host test: reconnect queues an internal stop command even when push-to-talk is still held. Disconnect alone does not stop the local recorder in the inspected standard 1.23.2 path. A disconnect followed by automatic reconnect therefore cuts off recording at the reconnect.

What happens

Bluetooth connects → blue connection cue + internal stop command → PTT ownership cancelled → local recorder stops → two stop buzzes

The connected callback calls app_package_mic_recording_stop_isr() unconditionally for HANDWARE_1_23_2. That queues 0x71 / 0xF9, the internal “stop offline recording” command. app_factory_ptt_before_command() treats this as a recorder ownership change and stops the recording before the normal command handler runs. The normal handler also handles 0xF9 by calling app_pdm_recording_stop().

This path needs no finger release, sensor fault, or timeout. It also cancels a gesture-started memo. Continued hold reports after cancellation do not restart capture; the PTT state requires a new release/hold cycle.

The default connection indicator is blue for approximately two seconds; the disconnect indicator flashes twice. The recorder’s separate stop routine emits two vibration pulses. The blue cue alone cannot establish whether audio ended, but the reconnect stop command provides a concrete explanation for the combined symptom.

App behavior

The current local app clears pending operations and recording presentation when disconnected. The inspected cancellation paths do not issue a local recording-stop command. On characteristic readiness, the app binds to factory recording events and schedules sync. Its automatic reconnection and stale-transfer recovery can trigger the firmware’s connected callback; the confirmed stop therefore happens without the app explicitly requesting it.

This is a current-source audit, not verification of the installed app binary. The closed vendor SDK’s internal behavior was not independently disassembled.

Implemented source fix

The new shared patch removes only the offline-stop enqueue from the connected callback. The disconnect callback, PTT state machine, deliberate stop commands, capture drain, and safe file close are preserved. Connection changes no longer revoke local recording ownership.

Both existing P11 variants receive an updated revision. Earlier preparation recipes remain unchanged:

Remaining release and physical verification

  1. Compile and qualify the new revisions with ArmCC5, then sign and publish through the established firmware release workflow.
  2. Add the P11-r3/r4 app labels and recognize the verified r4 package as Opus-compatible. The current app allows only r2 on a Ring reporting P11; retain the refusal for ADPCM-only or unknown packages when Opus files may exist.
  3. On the verified target and approved firmware candidate, test a held recording through a disconnect/reconnect and verify a single playable file containing audio before and after the transition. Check memo behavior and the stop gesture too.
  4. Separately improve indication priority so the active-recording light remains authoritative during Bluetooth status cues. This source fix preserves the existing connection cues.

The exact installed Ring revision has not been read back in this investigation. This confirms a defect in released P10-r2 software and a mechanism matching the reported symptom; it does not prove which transition occurred in a specific past incident. The fix is implemented in source; compiler verification, release qualification, and a physical regression test remain pending.
