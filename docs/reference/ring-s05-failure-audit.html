Production Ring 603V1.23.2 · Failure investigation · 9 September 2026

The GNU runtime port makes normal Ring callbacks reset.

The expanded audit reproduced six interrupt reset routes and stack-budget violations in three workers using the preserved S05 machine code. The leading cause of the failed connection is the mismatch between vendor interrupt callbacks and our new C-library lock backend. These failure paths do not require a recording.

Audited application: 8632de604b2bd79c103e43292e91eab4ba13aed1 · CI run 34237323221 · MBP-M5

September 10 software follow-up. The ArmCC 5 qualification report records the factory-identical baseline, repaired candidate and dispositions of these findings. This page and its original-binary reproducer remain historical failure evidence. Physical recovery and acceptance are still unresolved.

Evidence boundary. These defects were reproduced by executing the preserved application’s machine code in a Cortex-M4 CPU emulator. They fit the observed repeated connection/disconnection before service discovery. The Ring’s physical reset reason, actual RAM corruption and installed flash contents have not been read; the exact first fault on the device remains unmeasured.

1. The Bluetooth callback resets before it can handle the connection

The selected configuration sets NRF_SDH_DISPATCH_MODEL = 0, so SoftDevice events are dispatched in interrupt context. The final ELF’s SWI2 vector, event polling and BLE observer table route to the application callback. Its preamble logs every event except notification-complete, including BLE_GAP_EVT_CONNECTED.

SWI2 / EGU2 interrupt→ble_evt_handler→printf / Newlib lock→NVIC_SystemReset

DEBUG_INFO = 1 and BC_LOG_INFO still expands to printf. The GNU stdout stub returning an error does not eliminate formatting or lock acquisition. require_task_context() checks IPSR; any nonzero exception number calls contract_failure(), which resets the MCU.

Application callback          0x33304   IPSR = 38 (SWI2/EGU2)
printf                        0x74fb0
_vfprintf_r                   0x7b750
__retarget_lock_acquire_recursive 0x7356c
reset write instruction       0x73524   AIRCR[0xE000ED0C] = 0x05FA0004

The unchanged ELF requests the same reset with both cold and previously initialized stdio. This occurs before the connected-event switch body. The vendor logging call predates the GNU port; the reset-on-interrupt backend was introduced in commit 6d382ca. That integration mismatch is a concrete source defect independent of Opus.

Sources: bc_ble.c:279–284, bc_logger.h:27, sdk_config.h:11917, newlib_locks.c:50–82.

2. The clock reaches the same reset without a Bluetooth connection

app_init() starts the RTC path. With the selected 4095 prescaler and a 32,768 Hz RTC clock, ticks occur at 8 Hz. When the callback’s counter reaches seven, it increments the Unix time and calls bsp_rtc_get_date_time(). That function calls Newlib localtime(), whose timezone lock invokes the same interrupt guard.

RTC2 eighth tick→calendar conversion→localtime / timezone lock→NVIC_SystemReset
bsp_rtc_callback              0x2f908   IPSR = 52 (RTC2), count = 7
bsp_rtc_get_date_time         0x2f824
localtime / localtime_r        0x75668 / 0x75678
__tz_lock                     0x76044
__retarget_lock_acquire        0x73548
reset write instruction       0x73524   AIRCR = 0x05FA0004

The original instructions reproduce a reset on this tick. Under normal uninterrupted timing, that path is reached about one second after RTC ticks start; this is an expected software interval, not a measured reboot period on the Ring. Removing Bluetooth logging alone leaves this failure intact.

Sources: bsp_rtc.c:162–216 and 235–239, app_rtc_handler.c, app.c:103–107.

3. A 512-byte motor stack is too small for the linked logging path

The motor worker logs immediately on entering its loop. Its actual ELF task descriptor specifies 128 words: 512 bytes on this port. Executing the original worker from its entry through the return of its first log call, with initialized stdio, reaches a 664-byte stack depth and writes at that depth.

512 B allocated152 B beyond

664 bytes observed in the CPU model. Interrupt context-save overhead is not included.

This is stronger than a speculative stack-size warning: the reproducer observes actual writes below the 512-byte boundary. The model relocates the stack to an otherwise empty RAM region to measure usage; it does not model which neighboring heap object would be damaged on the Ring. The linked printf and _vfprintf_r entry frames alone consume 32 + 392 bytes before their deeper calls and the motor caller frame.

The continuation reproduced the same 664-byte depth in the hardware-check worker, and a 672-byte lower bound in the motion worker’s timer-creation helper. All three have 512-byte budgets in their actual ELF descriptors. configCHECK_FOR_STACK_OVERFLOW and configUSE_MALLOC_FAILED_HOOK are both zero. The LED worker’s selected S05 branch excludes its legacy logging; source text alone would have incorrectly implicated that path.

Sources: user_rtos_config.h:70 and 124, app_linear_motor_handler.c:61, 139–144 and 236–242, FreeRTOSConfig.h:142–148.

Another defect survives removing the logs. The motion GPIO callback then calls bc_rtos_timer_start(timer, 50), which expands to the task-context timer command with a nonzero wait. The original binary calls xTimerGenericCommand at 0x2b79a with command 1 and wait 50. Interrupt code must use the ISR-safe command or defer this work to a task. This is a confirmed source/binary API mismatch; its later runtime failure is masked by the earlier logging reset and was not separately emulated. See the official FreeRTOS timer API reference.

6. What the controls and broader checks establish

The original ARM Opus startup preparation returns success. The linked allocator, encoder initialization and silent-frame self-test execute 450,822 modeled instructions, reaching 4,872 B of stack depth in the helper. This uses initially free RTOS heap, zeroed DWT timing registers and no scheduling/peripheral model. It narrows the investigation; it does not qualify audio quality, sustained encoding, heap pressure, the complete worker stack or BLE coexistence.

The RTC first tick, zero-length BLE receive, and task-context lock controls return without resetting. These controls distinguish the reproduced faults from an emulator that simply resets on every entry. All target instructions remain unchanged.

The selected LittleFS mount path returns errors without automatically formatting the recording flash. App load bytes remain below the reserved flash region. No source/binary mismatch was found. Bootloader acceptance, installed flash contents, physical supply stability and reset reasons still require the failed Ring or a recoverable board.

The reset-on-interrupt backend first appears in commit 6d382ca on September 6, before the S05 Opus work. This is a runtime-port integration defect, not an Opus-specific requirement. The findings do not certify earlier engineering artifacts: each exact binary needs its own verification.

Why the checks did not catch this

sh tools/firmware/test.sh completed successfully again on MBP-M5 during this continuation. The results include the real codec suite (84,292 checks), 54 committed Opus fixtures, storage fault matrices, BLE routing, drivers, 4,634 SFUD transfer checks, 21 GNU heap-bound checks and 45 Newlib lock checks. One existing Python test was skipped. Host ASan/UBSan did not report a failing test; the log’s LittleFS “no more free space” line is from fault coverage.

  • The BLE harness extracts only the security/system-attribute switch cases. It omits the callback’s logging preamble and does not execute the linked ARM C library in an interrupt.
  • The lock harness expects the interrupt contract to fail. It verifies the guard while leaving the vendor callers outside its scope.
  • Host task tests run on host stacks and commonly stub logging. They do not apply the actual 128-word FreeRTOS task limits or the ARM Newlib call frames.
  • The GNU build summary proves source compilation, symbol definitions and static layout. Its “runtime lock audit” checks symbol presence and exclusion of the no-op backend; it does not prove runtime call-context compatibility.

Those checks remain useful within their scope. Their success was insufficient evidence for physical flashing. A Keil baseline build can establish a useful reference, but it does not by itself repair or qualify the GNU candidate.

Fix sequence before another device test

  1. Remove C-library locking work from interrupts. Use a bounded event buffer for logging and format in a worker. Move RTC calendar conversion/alarm evaluation to task context, or implement a reviewed lock-free integer conversion. Cover all six demonstrated routes, including Peer Manager, receive logging, PWM and motion GPIO. Replace task-only timer/tick APIs in interrupts, including the motion callback’s 50-tick timer command. Keep the guard; deleting it would expose the scheduler and library to unsafe interrupt use.
  2. Rebudget task stacks against the ARM binary. Remove unnecessary logs from small workers, size the remaining paths with margin, enable stack-overflow and allocation diagnostics, and account for exception/preemption overhead. Verify every active worker, timer task and the interrupt stack.
  3. Add integration tests that cross the missed boundaries. Exercise complete event callbacks with the intended dispatch context, RTC rollover after startup, and actual ARM libc call paths with task stack limits. Keep this original-binary reproducer as incident evidence; future firmware requires its own symbols and no-reset/no-overrun expectations.
  4. Qualify on a recoverable, identified spare. After a reviewed build and a verified recovery route, capture reset reasons, startup milestones, stack/heap margins, successful version readback, GATT/bonding, reconnect, recording and DFU re-entry. This audit performed no flashing or recovery operation.
